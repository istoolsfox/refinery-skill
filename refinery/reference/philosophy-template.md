# PHILOSOPHY.md 模板与提炼方法

> 项目哲学文件是 refinery A 模式的最高准则。五段结构，一页以内——
> 写不进一页的哲学没人执行。放项目根目录；新项目建议在项目脚手架/模板里内置本文件骨架。

## 提炼方法（A-greenfield：给没有哲学文件的项目起草）

1. **考古四处，按可信度排序**：
   - `docs/adr/` 的决策标题（每条 ADR 就是一条已拍板的哲学）；
   - README/SRS 的"不做什么"节（宗旨=项目决定不做什么）；
   - git log 里反复出现的修复主题（反复修什么，说明哲学里缺什么）；
   - 代码里反复出现的惯用法（错误处理形状、DI 方式、分层方式）——**代码是最诚实的哲学**。
2. **每条哲学必须能追溯到证据**（ADR 编号 / README 原文 / 代码示例），追溯不到的不写。
3. 草稿交用户确认后才定稿；确认前 Pass 3 用军规十条当临时标尺。
4. 已有零散文档（ADR、SRS、CLAUDE.md）→ 提炼归拢，标注出处，不要凭空新造。

## 模板

```markdown
# PHILOSOPHY — <项目名>

> 本文件是本项目代码的宪法。refinery / AI 协作 / 代码评审一律以此为准，
> 与通用规范冲突时本文件赢。修改本文件 = 修改项目方向，需要作者本人拍板。

## 1. 宗旨（这个项目决定不做什么）
- 不做：<…>（原因：<…>）
<!-- 从 SRS/README 的"不做什么"提炼，每条带一句为什么 -->

## 2. 设计哲学（三条以内，每条可执行）
1. <哲学> —— 出处：<ADR-XXX / README / 实践>
2. <哲学>
3. <哲学>

## 3. 风格三层
- 表层（工具管）：<formatter / linter 及其配置文件>
- 中层（惯用法）：<错误处理形状、命名传统、DI 方式、目录组织，各一句话+示例位置>
- 深层（哲学）：<为什么这个项目长这样，指向第 2 节>

## 4. 禁区（改代码时绝对不许）
- 禁止引入：<第三方运行时依赖 / 新的持久化层 / 全局单例 / …>
- 禁止绕过：<架构守卫测试 / 契约层 / …>

## 5. 机器命令（refinery 直接执行）
- lint：`<命令>`
- typecheck：`<命令>`
- test：`<命令>`
- 全量门禁：`<命令>`
```

## 好哲学条目的标准

- **可执行**：能据此判断一个具体 diff 该不该被接受（"保持简单"不合格，"不引入 X"合格）；
- **有出处**：ADR 编号或实践证据，不是愿景；
- **有代价自觉**：好哲学记录了"我们为此放弃了什么"（如零依赖哲学的代价是自己写 JSON 存储）。

## 维护

- 哲学文件 append 友好但修改敏感：改既有条目 = 推翻决策，走 ADR；
- refinery 每次优化发现"哲学漂移"（代码与哲学大面积不符）时报告，不擅自改哲学。
