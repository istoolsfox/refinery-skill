# 对抗自查（七视角红队）+ 报告规范

> 来源：作者开源贡献实战沉淀的七视角独立红队模板 + "双向独立交叉核对 > 单轮红队"原则，
> 裁剪到代码优化场景。执行方式：**用 Reviewer 的姿态重读自己的 diff**，假装不知道自己为什么这么改，
> 只看证据。发现任何一项不干净 → 回对应工序修，不许带病进报告。

## 七视角

### 1. 行为不变量（最重要的一个）
逐项回答：这次优化改变了什么可观察行为？函数签名、返回值、错误类型、日志输出、副作用顺序、
性能特征（哪怕复杂度不变，常数退化也算）、CLI/API 兼容性。
- 目标状态：清单为空，或每一项都有"这是申报过的行为变更 + 用户知情"的对应记录。
- 有清单外行为变化 → 回滚或申报，二选一。

### 2. 考卷完整性（测试纪律铁律 2 的红队复核）
diff 里搜：被修改/删除的测试文件、`skip`/`xfail`/`it.skip`/`@unittest.skip`、放宽的容差数字、
被删的断言行、阈值改动。每一个命中都必须有报告里的对应理由，缺一个 = 违规。

### 3. 死代码误判
对照 `dead-code-evidence.md` 四步证据链抽查自己的删除清单（抽 3-5 条，高危的必抽）：
动态调用排查做了吗？公共 API 边界判对了吗？有没有"只搜了源码、没搜配置和 CI"的？
启发式预扫的"候选"必须有证据链才能定案——作者实测中，预扫唯一候选最终是误报（实际在装配根使用）。

### 4. 范围蔓延
diff 里有没有与本次工序无关的改动？"顺手"改的命名、"顺便"加的防御性检查、"捎带"升级的依赖
——全是蔓延。无关改动：回滚，或单独拆出来说明并征得同意。优化的美德是克制。

### 5. 风格一致性
新代码像这个项目的代码吗（上游模式这题权重最高）：命名风格、错误处理形状、注释密度与语言、
import 顺序。自查法：把你的 diff 和同文件旧代码混在一起，读起来无违和才算过。

### 6. 性能回退
"简化"有没有把 O(n) 改成 O(n²)、把批量改成循环单查、把缓存删了、把惰性改成急切？
没有测量的地方，逐条对照改动前后做复杂度心算，可疑就标"未测量，建议基准"。

### 7. 可回滚性
- 改动是原子的吗？一个 revert 能整体还原吗？
- 死代码删除清单 + 测试删除清单完整吗？
- git 状态干净吗（没有 stage 到一半的文件、没有误改的无关文件）？

## 执行时机与记录

- 每道工序结束后快速过一遍相关视角（死代码工序重点过 2/3，原则体检重点过 1/4）；
- 全部工序结束后完整过一遍七视角；
- **>300 行或跨模块的改动：七视角逐条结论写进报告**；小改动报告里一句话带过。

## 优化报告模板（第 5 步交付物）

```markdown
# Refinery 优化报告 — <项目名>
- 日期：YYYY-MM-DD ｜ 模式：A 自有 / B 上游 / A-greenfield（附：PHILOSOPHY.md 草稿已出，待确认）
- 执行工序：Pass1 ✅ ｜ Pass2 ✅（删 N 项）｜ Pass3 体检+修复 M 项 ｜ Pass4 ⏭️ 跳过（原因：…）
- ⚠️ 无测试护栏声明：（仅当走了降级路径且无安全网时出现）

## 基线证据
- 测试：`<命令>` ｜ 基线 156 passed / 0 failed / 3 skipped → 终态 156 / 0 / 3
- lint/typecheck：`<命令>` ｜ 基线 X 问题 → 终态 0

## 改动清单
| # | 工序 | 文件 | 改了什么 | 为什么 | 证据 |
|---|------|------|----------|--------|------|
| 1 | P2 | src/foo.py | 删除 bar() | 全仓零引用（已排动态调用） | grep 摘要 |

## 发现但未动（含原因）
- P2 项：低耦合重复代码 ×2（见仁见智，动了收益小）
- 上游模式项：…（维护者裁决）
- 无测试区域：…（按铁律 4 应先补特征化测试）

## 测试纪律执行记录
- 基线：红/绿、skip 数
- 测试变更：无 / 有（逐条：测试名 + 随死代码删除的理由）
- 变异抽查：位置、注入内容、变红确认 ✅/该区域无看护的处理

## 红队结论
七视角逐条 pass/fail（大改动逐条展开，小改动一句话）
```

报告红线：允许说"本次没发现可优化项"（诚实是交付物），不允许交付一份没有基线数字的报告。
