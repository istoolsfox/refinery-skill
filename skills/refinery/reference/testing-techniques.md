# 测试方法工具箱（好办法库，按需加载）

> testing-protocol.md 管的是"AI 不许在测试上作弊"（纪律层）；
> 本页管"怎么把考卷出好、把测试写对"（方法层）。
> 理论底座：作者工程规范（测试金字塔/diff coverage/替换身纪律）、
> Feathers 遗留代码安全重构、变异测试（CRAP 思想：测试没机会变红 = 没有看护）、
> LLM 应用 evals 方法论（binary 断言优于打分、error discovery 优先）。

## 问题 1：考卷本身可能是假的（测试质量）

### 办法 A：变异测试打分（mutation testing）

唯一能**机器量化"测试真能抓 bug"** 的手段：工具往代码里注入变异（改边界值、删检查、返回错值），
看测试会不会红。全绿 = 你的考卷是摆设。

| 语言 | 工具 | 备注 |
|------|------|------|
| Python | mutmut / cosmic-ray | mutmut 上手快 |
| JS/TS | Stryker | 事实标准，支持 Jest/Vitest/Mocha |
| Rust | cargo-mutants | 当前社区首选 |
| Go | gremlins / go-mutesting | |
| Java | PIT | 最成熟 |

实操纪律：**按需跑**（很慢——只对核心模块、大重构后、或抽查跑）；分数当趋势不当硬门禁；
equivalent mutant（变了但行为等价的变异）靠人工判断，别追 100%。
与 testing-protocol 铁律 5（手工变异抽查）的关系：铁律 5 是零工具的轻量版，本表是可工具化的完整版。

### 办法 B：AI 生成测试三大病（评审 AI 写的考卷时逐条查）

1. **同义反复（tautological）**：断言只是把实现复述一遍（`assertEqual(f(x), 手工展开的计算过程)`）——
   实现写错了它也绿。查法：问"这个断言在实现完全写反时会不会仍然通过"。
2. **无边界**：只测 happy path。查法：对照边界清单（空输入/0/负数/极大值/None/超长/并发重复）逐个数，
   一个都没碰 = 打回。
3. **过度 mock**：mock 到被测对象只剩转发逻辑，绿了什么都没验证。查法：数 mock 行数 vs 断言行数；
   mock 只许出现在边界（DB 驱动/HTTP 客户端/消息发送器）。

红线（对 AI 和人同样生效）：断言必须断**业务可观察值**（返回值、落库内容、发出的消息），
不许断内部调用顺序；禁止无断言的测试（跑过≠验证过）。

## 问题 2：该测什么——覆盖行为，不是覆盖行

### 办法 C：性质测试（property-based testing）——AI 最适合的测试模式

AI 写"性质"（不变量），机器生成几百个用例去打它。人写例子容易漏，AI 写性质又快又好：

| 语言 | 工具 |
|------|------|
| Python | Hypothesis |
| JS/TS | fast-check |
| Rust | proptest |
| C++ | rapidcheck |

最适合的性质：解析/编码 round-trip（`decode(encode(x)) == x`）、排序后有序且元素不变、
金额计算守恒、协议解码对任意字节数组不崩、幂等性（同一请求执行两次结果不变）。

### 办法 D：diff coverage（盯增量不盯总量）

全仓覆盖率 80% 可能藏着"新改的代码 0% 被测"。看**变更代码被测试触及的比例**，
CI/报告里报 diff coverage，存量欠账单独列。

## 问题 3：LLM 功能本身怎么测（AI 应用的考卷）

### 办法 E：evals 方法论

- **error discovery 优先**：先跑 ~100 条真实 trace 收集失败案例，再谈断言；
- **binary 断言优于打分**："这条回复有没有把用户问的日期说对"（是/否）远比 1-5 分可靠；
- 人工抽核 ~30 条校准；评测集进版本库，当回归考卷用。

### 办法 F：确定性缝合

LLM 输出先过**结构化校验**（JSON schema / 枚举白名单 / 关键字段必填），测试只测结构+关键决策；
自然语言部分人工抽审。三值决策器（如 reply/listen/nudge 类状态路由）就是现成范本。

## 问题 4：工程化（让好办法跑得起来）

- **变异测试慢** → 增量跑（只变异本次改动 + 受影响测试）、CI 定时全量；
- **flaky 治理** → 注入时钟/固定随机种子（时钟抽象 + FakeClock 注入是范本）；
  隔离重试 + `@flaky` 标记 + issue，不许长期放着污染信任——一个常绿的假测试比没有测试更糟；
- **无测试区** → golden master / 快照审批测试（测当前行为而不是期望行为，diff 就是变更审查材料）；
- **架构守卫测试** → 分层/依赖方向规则写成测试（架构测试机器强制是范本），
  这是"设计哲学变考卷"的终极形态。

## 使用时机（refinery 内）

- Pass 3/4 动了核心逻辑 → 建议对该模块跑一次变异测试打分（有工具就用，没工具就手工铁律 5）；
- 需要补测试（铁律 4/降级路径）→ 优先性质测试 + 边界清单，杜绝三大病；
- 项目含 LLM 组件 → 按 evals 方法论出考卷；
- 以上都是**建议项**，不改变 testing-protocol 五铁律的强制地位。
