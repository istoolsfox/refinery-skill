# Refinery 三模式细则

> 模式错配是本 skill 最大的风险源：把自己的规范强加给别人的项目，等于在上游 PR 里发动风格战争
> （实战教训：拒 PR 措辞表、同题三度撞车后才学到"开 PR 前先搜同题"）。定档宁保守勿激进。

## 判定流程

```
有 git remote 吗？
├─ 无 remote（纯本地项目）→ A 自有项目
└─ 有 remote
   ├─ origin 属于你自己的账号 → A 自有项目
   ├─ origin 指向别人 / 存在 upstream remote / 本地分支与上游同步 → B 上游贡献
   └─ 分不清 → B 上游贡献（保守档）
```

**自有账号判定**：recon.sh 依次取 `REFINERY_OWN_USER` 环境变量 → `git config --get github.user`；
都拿不到则输出"待判定"，此时按 B 档保守处理（可在报告里注明原因）。

辅助信号：仓库有非本人署名的维护者提交记录、README 口吻是第三方、
你自己的贡献笔记里登记过该仓库、本地有 fork 常备的备份分支 → 都是 B 档证据。

## A 自有项目模式

规范适用级别：你的个人规范集（`REFINERY_NORMS_PATH`，未设置则 SKILL.md 内嵌的十条军规）+ 项目内约定（AGENTS.md/CLAUDE.md 等）全量适用。

### A-1 有 PHILOSOPHY.md（或等价的 AGENTS.md/CLAUDE.md 哲学节）

- 它是本项目的最高准则，优先级高于通用规范——**冲突时哲学文件赢**。
- 体检（Pass 3）以它为标尺；禁区（"不许引入 X"）绝对遵守。
- 发现哲学文件与代码大面积不符 → 报告"哲学漂移"，让用户决定改代码还是改哲学。

### A-2 无 PHILOSOPHY.md（A-greenfield 草案路径）

1. **考古**：git log 高频主题 → README"不做什么" → docs/adr/ 决策 → 代码里反复出现的惯用法
   （错误处理形状、命名风格、DI 方式、目录分层）。
2. **起草**：按 `philosophy-template.md` 生成草稿，写到项目根 `PHILOSOPHY.md`。
3. **交用户确认**：草稿必须给用户过目拍板后才算数；用户没确认前，Pass 3 以军规十条为临时标尺，
   并在报告里注明"标尺为通用规范，项目哲学待定稿"。
4. 已有成熟文档（ADR、SRS"不做什么"、CLAUDE.md）→ 提炼归拢并标注出处，不要凭空新造。

## B 上游贡献模式（别人的项目）

**核心立场：这个项目的风格不是你的规范，是它的历史。你的规范集在这里只是"自查镜"，
用来发现自己改动里的低级错误，永远不是改别人代码的依据。**

### 默认动作：体检报告，不动代码

用户只说"优化/体检"这类笼统指令时，B 模式只产出报告：

- 用上游自己的工具跑 lint/typecheck/test，报告现状；
- 发现清单按上游视角写（"维护者可能怎么看"），不用 P0/P1 分级；
- 不建议上游装你的工具链；不写任何文件进仓库。

### 用户明确要求改代码时（通常是为了提 PR）

1. **风格三层收敛**（顺序不可颠倒）：
   - 表层：上游的 formatter/linter 说了算，配置一字不改；
   - 中层：模仿相邻代码的惯用法（同文件怎么写你就怎么写）；
   - 深层：考古宗旨——看 merged PR、维护者的拒绝评论、CONTRIBUTING、issue 讨论，
     弄清"这个项目为什么长这样"。宁可不动，不可违旨。
2. **行为变更先问 intended**：任何改变对外行为的"优化"，先去 issue 问
   "Is this intended?"，附复现证据；拿到维护者方向再动手
   （真实案例：行为变更未先问 intended 的 PR，排了两周队后被维护者以
   "correct behaviour" 关闭——优化无错，方向不对）。
3. **纯清理类 PR 通常不受欢迎**：死代码删除、大规模重命名这类"没修任何东西"的改动，
   默认不主动提 PR；除非维护者明确邀请（issue 里说过 "PR welcome"）或它阻塞你真正的修复。
4. **测试跟上游**：跑 CONTRIBUTING 指定的命令；新测试模仿上游测试风格；永不引入自己的测试框架。
5. **不发车红线**：改完不 push，diff 交使用者审（纪律：一切对外 PR/评论草稿审后发）。

### B 模式下你的规范集用在哪

只剩两处：①自查自己的改动有没有引入上游没有的坏味道（未处理错误、调试残留）；
②写 PR 描述时借用评审检查单自查完整性。仅此而已。

## 模式速查

| 情境 | 模式 | 动作 |
|---|---|---|
| 自己的项目，有哲学文件 | A-1 | 全量优化，哲学优先 |
| 自己的项目，无哲学文件 | A-2 | 起草哲学 → 用户确认 → 优化 |
| 别人的仓库，笼统说"优化" | B | 只出报告 |
| 别人的仓库，明确要改 | B | 风格收敛 + 行为变更先 issue + 改动不 push |
| 分不清是谁的 | B | 保守处理 |
